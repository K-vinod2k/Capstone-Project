# Why your Unitree G1 ragdolls in MuJoCo and how to fix it

Your G1 collapsing within 3–4 seconds is almost certainly an actuator configuration problem — most likely **`biastype="none"`**, which silently disables all position feedback and turns your robot into a passive ragdoll. This is the single most common pitfall in MuJoCo humanoid simulation, and multiple community members have hit the exact same wall (see IsaacLab issue #3751, where a G1 "collapses immediately upon simulation start"). The good news: the community has extensive working configurations, and projects like MuJoCo Playground have achieved **zero-shot sim-to-real transfer** on the G1 with under 30 minutes of training. Below is everything you need to diagnose and fix your pipeline.

## The biastype silent failure is probably your culprit

MuJoCo computes actuator force as `force = gain × ctrl + bias`, where bias depends entirely on the `biastype` parameter. When `biastype="none"` (value 0, the default for `<general>` and `<motor>` elements), **all `biasprm` values are silently ignored** — the bias is hardcoded to zero in MuJoCo's `engine_forward.c`. This means your actuator produces only `force = gain × ctrl` with absolutely no position or velocity feedback, regardless of what you put in `biasprm`. The robot has zero joint stiffness and drops under gravity.

The fix requires `biastype="affine"` (value 1), which computes `bias = b0 + b1 × position + b2 × velocity`. A proper PD position servo needs `gainprm="kp"` and `biasprm="0 -kp -kd"`, producing `force = kp × (target − position) − kd × velocity`. The `<position>` shortcut element sets this automatically, but if you're using `<general>` elements (common in retargeting pipelines), you must set biastype explicitly. **Run this diagnostic immediately**: print `model.actuator_biastype` — if any values are 0 for joints that should hold position, that's your bug. Also check `data.actuator_force` during simulation; if forces are near-zero or constant despite non-zero ctrl, the actuators aren't doing PD control.

Four distinct misconfiguration patterns cause ragdolling. First, `biastype="none"` with biasprm set (biasprm silently ignored). Second, positive biasprm signs (`biasprm="0 200 50"` creates positive feedback — explosive instability). Third, missing velocity damping (`biasprm="0 -kp 0"` causes violent oscillation). Fourth, actuator gains too low relative to body mass — the G1 weighs ~35 kg, so kp values below **40 N·m/rad** on leg joints can't overcome gravity.

## Working G1 MuJoCo configurations and the gains that matter

The MuJoCo ecosystem has **three main G1 model sources**, each with different actuator philosophies. The **mujoco_menagerie** repository (google-deepmind) provides `g1.xml` with `<position>` actuators (which the README explicitly notes "needs tuning") and `g1_mjx.xml` with tuned `<general>` actuators using `biastype="affine"` with "lower, more realistic PD gains" — this is the version that was **successfully transferred to real G1 hardware** via MuJoCo Playground. The **unitree_mujoco** repository uses `<general>` or `<motor>` actuators designed for direct torque control via Unitree SDK2, where PD is computed externally. The **LeRobot/GR00T-WBC** model (`lerobot/unitree-g1-mujoco` on HuggingFace) runs at 500 Hz and provides the most thoroughly documented PD gains.

Here are **confirmed working PD gains** from multiple sources:

From the GR00T Whole-Body Controller (NVIDIA), validated in simulation and on hardware: hip joints use **kp=150, kd=2**; knee joints use **kp=300, kd=4**; ankle joints use **kp=40, kd=2**; waist joints use **kp=250, kd=5**; shoulder joints use **kp=100, kd=2–5**; elbow/wrist joints use **kp=20–40, kd=1–2**. From Unitree's own `unitree_rl_gym` (g1_config.py): hip yaw/roll/pitch all use **kp=100, kd=2**; knee uses **kp=150, kd=4**; ankle uses **kp=40, kd=2**. The MOSAIC paper takes a more principled approach, computing per-joint gains from a second-order system model with **damping ratio ζ=2.0** and natural frequency derived from joint armature.

The pattern is clear: **legs need dramatically higher gains than arms** (knee kp=150–300 vs wrist kp=20), and the gains are not uniform across joint groups. If you're using a single kp/kd for all joints, that's likely contributing to instability.

For XML configuration, use the `scene_mjx.xml` from menagerie as your starting point — it has hand-tuned collision geometries, solver iterations, and the proven-working PD gains. Set your initial pose using the `home` or `stand` keyframe (`mujoco.mj_resetDataKeyframe(model, data, keyframe_id)`), and use a **2 ms timestep** (500 Hz) which is the community standard for G1 simulation.

## The retargeting pipeline from SMPL-X to G1 has known solutions

Your pipeline (PromptHMR → SMPL-X → retargeting → MuJoCo → G1) maps directly to several working open-source projects. **GMR (General Motion Retargeting)** from Stanford is the most directly applicable — it has a one-line command `python scripts/smplx_to_robot.py --smplx_file <path> --robot unitree_g1` that handles SMPL-X to G1 retargeting with automatic coordinate frame conversion. GMR uses a two-stage IK optimization (first position-only to avoid local minima, then position + orientation) with non-uniform per-body scaling to handle limb length differences between human and robot.

The critical coordinate frame issue: **SMPL/SMPL-X uses Y-up** (person upright along Y-axis), while **MuJoCo uses Z-up** (gravity in −Z). This requires a 90° rotation around the X-axis. GMR handles this automatically in its rest-pose alignment step, but if you're doing custom retargeting, a missed or incorrect frame transformation will produce poses where the robot thinks "standing" means lying on its back. PHC (Perpetual Humanoid Control) adds another wrinkle — it uses a modified coordinate system with −Z gravity and the humanoid facing +X, which requires explicit transformation to convert back to standard SMPL coordinates.

Beyond coordinate frames, the **kinematic mismatch** between SMPL-X (54 joints) and the G1 (23–29 joints) demands careful joint correspondence mapping. The H2O project defines 6 key tracking points (ankles, shoulders, elbows); ExBody maps 9 upper-body joint positions plus 18 keypoint coordinates; GMR defines per-body mapping with custom scale factors. ExBody's key insight is to **NOT try to exactly replicate lower-body motion** — it tracks upper body through joint angles and keypoints while the lower body only follows velocity commands, because human-robot lower-body kinematics diverge too significantly for direct imitation.

A critical post-processing step that many pipelines miss: after retargeting, run forward kinematics on the output, compute the minimum body height per frame, and subtract the mean to fix floating/penetration artifacts. PHC's post-processing can produce **30+ cm floating artifacts** without this correction. GMR's non-uniform scaling avoids most of this at the source.

## Sim-to-real transfers that actually worked on the G1

Multiple groups have achieved robust G1 sim-to-real transfer, with consistent lessons. **MuJoCo Playground** (Google DeepMind, arXiv 2502.08844) trained a joystick locomotion policy for the 29-DoF G1 in MuJoCo's MJX backend, achieving zero-shot transfer to real hardware in under 30 minutes on two RTX 4090s. Policy inference runs at **50 Hz** with a model-based estimator at the hardware communication rate (500–2000 Hz). The key was using the `scene_mjx.xml` model with its hand-tuned collision pairs and realistic PD gains.

**ASAP** (CMU + NVIDIA, RSS 2025, arXiv 2502.01143) demonstrated the G1 performing kicks, jumps, and athletic celebrations. Their most important finding: the G1's **ankle parallel mechanism** creates the largest sim-to-real gap. They trained a delta action model specifically for the 4 ankle DoFs to compensate for dynamics mismatch, reducing tracking error by up to **52.7%**. Two G1 robots broke during data collection from motor overheating during agile motions — a sobering reminder of real-world constraints. The gait-conditioned RL approach (arXiv 2505.20619) achieved standing, walking, and running with zero-shot transfer using biomechanics-inspired reward shaping and no motion capture references.

The **29-DoF vs 23-DoF joint mismatch** is handled differently across projects. The G1 EDU Plus has 29 DoF (12 legs + 3 waist + 14 arms including wrists), while the base model has 23 DoF. ASAP uses a `g1_29dof_anneal_23dof` configuration that trains with 29 DoF but anneals to 23 for deployment by locking wrist and extra waist joints. The LeRobot model notes that **missing joint observations must be zeroed at indices 12, 14, 20, 21, 27, 28** — a subtle but critical detail for policy transfer.

All successful sim-to-real projects share common practices: **domain randomization** of mass, inertia, friction, and PD gains during training; early termination when pelvis height drops below 0.3 m; motion filtering to remove physically infeasible SMPL sequences (typically discarding 20–30% of motions); and starting/ending motions on stable standing poses.

## A diagnostic and repair checklist for your specific pipeline

Given your symptoms (ragdoll collapse in 3–4 seconds), work through this diagnostic sequence. First, **check actuator configuration**: print `model.actuator_biastype` and verify all values are 1 (affine), not 0 (none). Print `data.actuator_force` at each timestep — if forces are near-zero, your actuators aren't producing feedback. Second, **verify PD gains**: use the GR00T values as a baseline (kp=150/300/40 for hip/knee/ankle, kd=2/4/2). Third, **check coordinate frames**: visualize your retargeted pose in MuJoCo before running dynamics — if the G1 appears in a non-standing configuration, your SMPL-X → MuJoCo frame transformation is wrong (remember Y-up to Z-up). Fourth, **validate joint angles against limits**: the G1's joint limits are defined in the MJCF; retargeted poses exceeding these limits will cause immediate instability. Fifth, **try the standing pose without your pipeline**: load the menagerie model, reset to the `stand` keyframe, set `ctrl = qpos` for all position actuators, and confirm the robot holds position. If it does, the problem is in your retargeted poses or controller; if it doesn't, the problem is in your model/actuator configuration.

For your specific PromptHMR → G1 pipeline, the recommended path is to replace custom retargeting with **GMR's `smplx_to_robot.py`**, which handles coordinate frame conversion, limb-length scaling, and joint-limit enforcement automatically. Filter the output through a feasibility check (projected CoM within support polygon, joint angles within limits, no self-collisions), and use the `g1_mjx.xml` model from menagerie at 500 Hz with the proven PD gains.

## Conclusion

The ragdoll problem is almost always an actuator misconfiguration rather than a fundamental simulation issue — the community has repeatedly demonstrated stable G1 standing, walking, and even athletic maneuvers in MuJoCo. The three most impactful fixes are ensuring `biastype="affine"` on all position actuators, using per-joint-group PD gains calibrated to the G1's mass distribution (not uniform gains), and correctly transforming SMPL-X's Y-up frame to MuJoCo's Z-up frame during retargeting. For your pipeline specifically, GMR provides the most direct SMPL-X → G1 retargeting path with automatic handling of the coordinate and kinematic mismatches that typically cause pose-transferred robots to collapse. Start with the `scene_mjx.xml` menagerie model and GR00T PD gains — these represent the community's most battle-tested configuration for the G1 in MuJoCo.
